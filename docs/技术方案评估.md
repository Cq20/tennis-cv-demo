# Good-Tennis + MediaPipe 整合方案技术评估

**评估日期**：2026-09-02
**评估对象**：四层架构（视频输入 / 视觉感知 / 动作分析 / 展示）+ MediaPipe 姿态 + SVM 动作分类
**Good-Tennis 版本依据**：`yo-WASSUP/Good-Tennis`（已支持 YOLO 人体 + 网球检测、球场映射、球员追踪、回合检测、小地图、热力图/散点图、数据导出；球员检测可切换 RTMPose / RTMO / Ultralytics YOLO-Pose）

---

## 0. 总体结论

**技术可行性：中高。方案主体可落地，但有两个结构性问题必须先解决，否则会停在"跑通了但结果不可信"的状态。**

| 结论项 | 判断 |
|---|---|
| 分层思路 | ✅ 合理，是标准 CV 管线，方向正确 |
| 整合路径（先跑通 Good-Tennis 再插桩） | ✅ 正确，强烈赞成，不要并行开发 |
| 插入 MediaPipe | ⚠️ **不推荐** —— Good-Tennis 已内置姿态后端（RTMPose/RTMO/YOLO-Pose），引入 MediaPipe 会导致「双姿态栈」且丢掉 track_id 绑定 |
| SVM 分类 | ⚠️ **被高估** —— 规则 + 已有回合检测可覆盖约 80%，SVM 应作为第二阶段增量而非第一步 |
| 方式 A / B | ✅ **选 A（离线批处理 JSON）**，但建议演进为 A+（异步任务队列 + 进度推送） |
| 最大隐藏风险 | 🔴 **缺失「击球事件切分」与「球员身份绑定」两层** —— 这是动作分析的输入锚点，缺了它 L3 无从下手 |

**一句话建议**：把"插入 MediaPipe"改成"复用 Good-Tennis 已有的姿态后端"，把"训练 SVM"改成"先做击球事件切分 + 规则判定"，把"实时流"改成"离线批处理 + 进度条"。改动后工作量下降约 40%，可信度显著上升。

## 1. 架构分层与数据接口设计评估

### 1.1 分层评价

四层切分符合「感知 → 语义 → 呈现」的经典范式，职责边界清晰，本身没问题。但存在两处**结构性缺口**：

**缺口一：L2 与 L3 之间缺「事件与身份层」（关键）**

L2 输出的是**逐帧的、无身份的、无事件结构的**检测流；L3 需要的是**以击球事件为单位的、绑定到具体球员的**时序片段。这两者之间不是简单的数据格式转换，而是一个需要独立设计的算法模块：

- **击球事件切分**：确定"第几帧发生了击球"。没有这个，SVM 就只能在每一帧上盲目分类，而正手/反手在远离击球点的帧上角度分布高度重叠，分类必然退化成随机猜测。
- **球员身份绑定**：画面上有两个人（甚至还有裁判、捡球童）。分析结果必须归属到"谁"。且 YOLO tracker 在遮挡后会 ID switch，同一球员中途可能被切成两个 track_id。

**缺口二：L3 与 L4 之间缺「存储与任务层」**

这一层决定了实时还是离线、能否断点续跑、能否复现。它同时是方式 A 与方式 B 的分水岭（见第 3 节）。

### 1.2 数据接口设计建议

**核心原则一：以「帧索引」为主键，绝不用 wall clock。**

视频处理速度 ≠ 视频播放速度。所有时间戳统一到 `frame_index`，再派生 `timestamp_ms = frame_index / source_fps * 1000`。用 wall clock 会在抽帧、掉帧、续跑时全部错位。

**核心原则二：逐帧数据用 JSONL（每行一个 JSON），聚合结果用 JSON。**

不要输出一个嵌套的大 JSON。理由：可流式写入（边处理边落盘，崩溃不丢全量）、可流式读取（前端边下边渲染）、可断点续跑（读到第 N 行就接着处理）、体积可控。

```jsonl
{"f":0,"t":0,"players":[{"tid":1,"side":"near","bbox":[812,433,96,210,"xywh"],"court":[4.21,11.03],"pose":[[x,y,v],...],"world":[[x,y,z],...],"ang":{"elbow_r":142.3,"elbow_l":98.1,"shoulder_r":67.2,"torso_rot":-23.4,"knee_r":155.0}}],"ball":{"xy":[903,512],"conf":0.82,"court":[3.9,10.8],"v":18.4,"interp":false},"ev":[]}
{"f":1,...}
```

```json
{
  "meta": {
    "source_file": "rally_001.mp4",
    "source_w": 1920, "source_h": 1080, "source_fps": 30.0,
    "total_frames": 18000, "processed_frames": 18000,
    "display_w": 1920, "display_h": 1080,
    "homography_segments": [{"start":0,"end":8420,"H":[...9 floats...]},
                            {"start":8421,"end":18000,"H":[...9 floats...]}],
    "pipeline_version": "1.0.0",
    "models": {"player":"yolov8s.pt","ball":"tennis_v3.pt","pose":"rtmpose-m"}
  },
  "events": [
    {"id":1,"type":"hit","frame":1240,"t_ms":41333,"player_tid":1,"side":"near",
     "stroke":"forehand","conf":0.87,"method":"rule",
     "contact_xy":[903,512],"contact_court":[3.9,10.8],"ball_speed_out":24.6},
    {"id":2,"type":"bounce","frame":1258,"t_ms":41933,"court":[6.2,14.1]}
  ],
  "summary": {
    "rallies": 12,
    "by_player": {"near": {"shots":87,"forehand":41,"backhand":33,"serve":13,
                           "distance_m":1240.5,"top_speed_ms":4.8}},
    "by_type": {"forehand":41,"backhand":33,"serve":13}
  }
}
```

**核心原则三：前端叠加必须携带显示元数据。**

这是纯 HTML 前端叠加骨骼时最常见的错位原因：`<video>` 的 `object-fit` 与 letterbox 会让"归一化坐标"对不上实际渲染区域。必须在 `meta` 里带 `source_w/source_h/display_w/display_h`，前端按实际渲染尺寸换算，而不是假设铺满容器。

### 1.3 体积预算（很容易被低估）

10 分钟 1080p@30fps 视频 = 18000 帧 × 2 人 × 33 点 × 3 float = **约 356 万个数字**。JSON 明文约 **40–60 MB**，前端 fetch 后解析会明显卡顿。对策：

| 手段 | 收益 |
|---|---|
| float 量化到 2 位小数 | −40% |
| 只对击球窗口 ±15 帧存全量 pose，其余帧只存 bbox + court_xy | **−90%** |
| 轨迹/热力图预处理成聚合数组，不逐帧传 | 前端零计算 |
| 必要时换 MessagePack / Float32Array + ArrayBuffer | 再 −50%，解析近乎零成本 |

**建议：默认只导出"事件窗口内的 pose"，其余帧只存轨迹点。** 大多数展示需求根本不需要全程骨骼。

## 2. 技术风险与难点逐项评估

### 2.1 🔴 高风险

**R1. MediaPipe 是单人姿态，与双人场景冲突**

MediaPipe Pose（BlazePose）本质是单人模型，官方推荐用法是「先有人体检测器给出 ROI，再在 ROI 内跑姿态」。网球画面里同时有**两名球员**，如果直接全图跑 `num_poses=2`，会出现关键点在两人之间跳变、遮挡时串人。而且 MediaPipe 输出的姿态**不带 track_id**，你需要自己把它和 YOLO 的 track_id 关联，这个关联本身就是个易错模块。

> **对策（强烈建议）**：放弃 MediaPipe，直接用 Good-Tennis 已支持的 **RTMPose / RTMO / YOLO-Pose**。它们是 top-down 多人姿态，**天然复用 YOLO 的人体框和 track_id**，身份绑定是免费的，还省掉一套依赖。这直接消解了你列为难点的"球员检测框与姿态关键点的对应"。
>
> **如果因故必须用 MediaPipe**：则必须实现 crop 映射链路 —— YOLO bbox 外扩 12–18%（外扩不足会截断肢体，过度会混入对方球员）→ 裁剪 → MediaPipe 推理 → 把 landmark 从 crop 坐标映射回全图坐标 → 校验 landmark 质心是否落在原 bbox 内 + 可见度阈值过滤 → 丢弃不合格帧。这段代码约 80 行，且是后续 bug 的主要来源。

**R2. 缺失击球事件切分（方案完全没提，但它是前置条件）**

SVM 要在哪一帧分类？你没定义。这是方案里最大的逻辑断层。

> **对策**：用 Good-Tennis 已有的球轨迹 + 球员位置做低成本检测：
> 1. 计算每帧「球心 ↔ 球员持拍侧手腕/球拍」的像素距离曲线
> 2. 取曲线局部极小值（< 阈值，如 60px）作为候选击球点
> 3. 用球速矢量方向的突变（夹角 > 60°）做二次确认
> 4. 最小间隔约束（如 0.4s）去重
>
> 这个信号不需要训练数据，纯几何规则，且球轨迹数据 Good-Tennis 已经算好了。它是后面所有动作分析的时间锚点。

**R3. 相机移动导致球场映射整体失效**

Good-Tennis 的球场映射基于一个固定的 homography。但：
- 转播机位是 PTZ 的，会平移/变焦
- 手机手持拍摄会抖
- 剪辑过的视频有镜头切换

任何一种情况下，用单一 homography 映射整段视频，球员轨迹和热力图都会严重失真，而且是**静默失真**——图看起来很漂亮，数字全是错的。

> **对策**：加一个镜头切分前置步骤。逐帧计算相邻帧的灰度直方图相关性 + 特征点匹配内点率，突变处切分；每个镜头段单独计算 homography 并做几何校验（映射后球场尺寸应接近 10.97m × 23.77m，误差 > 8% 则该段判为不可靠并降级为"仅相对坐标"）。`meta` 里存 `homography_segments` 数组（见 1.2 的 schema）。**这一步不做，后面所有位置类统计都不可信。**

### 2.2 🟡 中风险

**R4. SVM 训练数据的来源与规模**

你问到这一点，直接回答：

- **规模**：关节角度是低维特征（8–15 维），SVM 不需要大数据。**每类 150–250 个标注样本**（共 450–750 个击球事件）就能收敛；超过 2000 个后收益急剧递减。真正决定上限的不是样本量，是**样本覆盖的多样性**（不同机位、不同打法、不同体型、左右手）。
- **来源优先级**：
  1. 公开数据集：`TennisDB`、`Tennis-Mocap`（如有授权）、`Sports-1M` 子集
  2. **自采 + 手工标注**：这是最现实的路线。你有 Good-Tennis 的击球事件切分后，标注工作从"逐帧看"降级为"给每个击球片段打个标签"，一个 10 分钟视频约 100–150 个击球事件，人工标注约 15 分钟
  3. **半自动标注（推荐）**：先用下面 2.3 节的规则生成伪标签 → 人工只复核低置信度样本 → 用清洗后的数据训练 SVM。这样标注成本降到 1/5
- **必须做**：三段划分（train/val/test）+ **按视频切分而非按样本随机切分**（同一视频的帧高度相关，随机切会严重高估准确率，这是动作识别领域最常见的评估陷阱）

**R5. 关节角度的泛化性 —— 你的担心方向偏了**

> "关节角度对不同身高体型的泛化性"

**身高体型不是主要问题**——角度本身是尺度不变的，一个 1.6m 和一个 1.9m 的人做同一个正手，肘角数值接近。真正破坏泛化的是：

1. **相机视角**：这是头号杀手。2D 关键点算的"关节角度"是**投影角度**，不是真实三维关节角。侧机位下前臂的投影角度误差可达 30–40°，足以让 SVM 全盘失效。广播机位（高位后方）相对稳定，手机侧拍基本不可用。
2. **球员朝向**：需要一个"躯干朝向"特征把身体坐标系对齐。
3. **个体动作风格**：有人引拍幅度大，有人小。

> **对策**：
> - **用 world landmarks（米制 3D）而非 image landmarks 算角度**。这是最高性价比的一步改进，直接消除大部分视角畸变。MediaPipe 和 RTMPose（部分模型）都提供 world 坐标。
> - **做 per-subject 归一化**：减去该球员的静止基准角度，用"相对变化量"而非"绝对角度"作为特征。
> - **构造视角无关特征**：角度用关节三点构成（天然旋转不变），距离除以躯干长度（肩中点→髋中点）归一化。
> - **数据增强**：训练时对 keypoint 做轻微的 2D 仿射扰动 + 时间轴抖动，模拟不同机位。

**R6. 光照与遮挡鲁棒性**

- **人体姿态（MediaPipe/RTMPose）**：相对鲁棒。人是画面中的大目标，现代姿态模型在硬地阴影条纹、逆光、黄昏下表现尚可。主要失效场景是**两名球员重叠**（网前截击）和**快速挥拍的运动模糊**（关键点抖动）。
- **网球检测**：**这才是真正的难点，也是你方案中低估的部分**。球直径约 6.7cm，在 1080p 广角画面里只有 8–15 px；球速 30–60 m/s，在 30fps 下每帧移动 1–2 m，画面上是拉长的残影甚至完全消失。Good-Tennis 自己也标注"弹跳点检测仍在迭代中，适合研究和二次开发"。**不要指望球检测稳定，要通过轨迹插值/滤波来兜底。**
- **对策**：
  - 姿态关键点加**时序平滑**（One Euro Filter 或 Savitzky-Golay，窗口 5–7 帧）。注意：平滑必须在角度计算**之前**做，别平滑分类结果。
  - 球轨迹用**双向插值**（离线场景可以用未来帧，这是离线相对实时的又一大优势）。
  - 对低置信度帧输出 `interp: true` 标记，前端用虚线绘制，别让用户把插值数据当真。

### 2.3 🟢 被高估的环节：SVM 可能是多余的

**正手/反手/发球这个三分类问题，规则解法已经能覆盖大部分场景：**

| 判定 | 规则 | 数据来源 | 预期准确率 |
|---|---|---|---|
| **发球** | 回合的第一拍（Good-Tennis **已有回合检测**）+ 击球点 y 坐标接近球员最高点 + 击球点在底线后 | 现成 | 95%+ |
| **正手 / 反手** | 持拍手别（可由击球点长期分布推断：右手持拍者的正手击球点集中在身体右侧）+ 击球瞬间的球心 x 相对躯干中轴的方位 | 需 20 行代码 | 85–92% |
| **上手/高压** | 击球点 y 高于头顶 | 现成 | 高 |

这意味着：**你的第一个可用版本根本不需要训练任何模型。** 先上线规则版，用它生成伪标签，人工复核低置信度样本，再训练 SVM 作为增量。**顺序反了会浪费大量时间在标注上，而标注又依赖事件切分——方案里这个依赖链是断的。**

如果最后确实要上 SVM，特征工程建议（比原始角度更有效）：

```
每个击球事件，取 [contact-12, contact+8] 共 21 帧窗口：
  - 逐帧：elbow_r, elbow_l, shoulder_r, shoulder_l, torso_rot, wrist_speed, hip_shoulder_sep
  - 窗口统计：mean, std, max, min, argmax位置 → 8 维 × 5 统计 = 40 维
  - 事件级：击球点相对躯干的方位角、击球点高度 / 身高、挥拍峰值速度
  - 分类：RBF-SVM（先 StandardScaler + PCA 到 20 维），或直接用 RandomForest / LightGBM
```

用窗口统计量而非单帧角度，是把"时序信息"喂给无时序模型的最简单做法，比单帧特征通常高 8–15 个点。

## 3. 方式 A vs 方式 B：取舍建议

### 3.1 结论：选 A，并演进为 A+

| 维度 | 方式 A（离线 JSON） | 方式 B（WebSocket 实时流） |
|---|---|---|
| **算法准确率** | ✅ 可用**双向时序平滑**（前后帧都可见），轨迹插值、事件切分、ID 归并质量显著更高 | ❌ 只能因果推理（只看历史帧），准确率系统性下降 5–15 个点 |
| **算力要求** | ✅ 慢一点无所谓，可跑大模型、可多趟处理 | ❌ 必须实时，只能砍模型 |
| **架构复杂度** | ✅ 无状态，一个 JSON 文件 + 静态托管 | ❌ 有状态连接、断线重连、背压、会话管理、GPU 常驻 |
| **调试与复现** | ✅ 结果可存档、可 diff、可离线复现 | ❌ 瞬时即逝，bug 难复现 |
| **成本** | ✅ GPU 按需启动，处理完释放 | ❌ GPU 常驻，用户在线才用，利用率低 |
| **与你现有纯 HTML demo 的契合** | ✅ 完全契合，`fetch` 一个 JSON 即可 | ❌ 需要额外写 WebSocket 客户端与流控 |
| **延迟体验** | ❌ 需等待处理（分钟级） | ✅ 即时 |

### 3.2 决定性理由

1. **网球复盘天然是离线场景。** 用户打完球想看的是"这一小时的统计与热力图"，不是"我这一拍是什么"。安防监控才需要实时，网球分析不需要。
2. **实时在物理上就达不到。** 下面 4.2 的预算表显示，全栈跑满在消费级 GPU 上约 20–30 fps，而这已经是"刚好够"的水平；加上编码、传输、前端渲染，端到端延迟轻松超过 300ms，用户体验是"卡顿"而非"实时"。
3. **实时会牺牲准确率。** 双向 vs 单向平滑这一项就是 5–15 个点，这是不可逆的损失。

### 3.3 推荐路径：A+（异步任务队列）

既拿到 A 的简单与准确，又接近 B 的体验：

```
上传视频 → 后端落盘 + 生成 job_id + 立即返回（< 1s）
        → 任务入队（Celery / RQ / 后台线程）
        → GPU worker 处理，写 progress.json（0–100% + 当前阶段名）
        → 前端轮询 GET /api/jobs/{id}/progress（1s 间隔）
          或 SSE / WebSocket 仅推送进度（数据量极小，无背压问题）
        → 完成后前端拉 result.json + frames.jsonl 渲染
```

**关键点：WebSocket 只用来推"进度"这个几十字节的消息，不推视频帧。** 这样既规避了方式 B 的全部复杂度，又让用户不用干等着黑屏。

**什么时候才真的需要方式 B**：只有当产品需求是"发球动作即时纠正"这类**必须在现场马上看到反馈**的场景。即便如此，也建议降级方案——低分辨率（480p）+ 每 3 帧抽 1 帧 + 只跑姿态不跑球检测 + 只做关节角度提示不做完整分类。

## 4. 性能瓶颈分析

### 4.1 单帧耗时估算（1080p，RTX 3060 级别，FP16）

| 模块 | 模型 | 耗时 | 备注 |
|---|---|---|---|
| 人体检测 | YOLOv8s | 8–12 ms | 每帧必跑 |
| 网球检测 | 微调小模型 @1280 | 10–18 ms | **最大单项开销**，因需高分辨率输入 |
| 姿态估计 | RTMPose-m × 2 人 | 6–14 ms | 依赖检测框数量 |
| 坐标映射 / 追踪 / 绘图 | CPU | 2–5 ms | |
| **合计** | | **26–49 ms/帧** | **→ 20–38 fps** |

### 4.2 结论与瓶颈定位

**瓶颈不是 GPU 算力，而是：多模型串行 + Python GIL + 视频解码 I/O。**

- 10 分钟 1080p@30fps = 18000 帧，按 35ms/帧 计 → **约 10.5 分钟处理时长**（约 1× 实时）。
- 无 GPU（纯 CPU）时约 **8–15× 实时**，即一段 10 分钟视频要跑 80–150 分钟——**必须做任务队列和进度提示**，否则用户以为页面死了。

### 4.3 优化手段（按性价比排序）

| 手段 | 收益 | 代价 |
|---|---|---|
| **不要每帧都跑姿态** —— 检测阶段用低分辨率跑 YOLO，只对击球窗口 ±20 帧在原分辨率跑 pose | **−60% 总耗时** | 需要先有初筛信号（可用球员速度 + 球速阈值触发） |
| 统一推理后端到 **ONNX Runtime / TensorRT**（Good-Tennis 已支持 ONNX Runtime） | −30~50% | 一次性转换成本 |
| 解码用 **FFmpeg 管道 + 硬件解码（NVDEC）**，避免 OpenCV 逐帧 seek | −20% | 中等 |
| 批量推理：攒 8–16 帧 batch 送 GPU | −15~25% | 增加 8 帧延迟（离线无所谓） |
| 检测分辨率降到 640，姿态在 crop 上跑原生分辨率 | −25% | 小目标（球）召回下降 |
| 多进程流水线：解码 / 推理 / 写盘三段并行 | −20% | 复杂度上升 |

**内存**：18000 帧全量轨迹缓存在内存约 200–500 MB，尚可接受；但长视频（>1 小时）必须**流式写 JSONL**，不要攒到最后一次性 dump。

## 5. 被高估与被遗漏的环节

### 5.1 被高估（4 项）

| # | 你高估了 | 实际情况 |
|---|---|---|
| 1 | **SVM 的必要性** | 规则 + 已有回合检测可覆盖约 80%，且规则版可作为伪标签生成器 |
| 2 | **33 个关键点的价值** | 网球动作分析只需要 **11–13 个点**：双肩、双肘、双腕、双髋、双膝、双踝 + 鼻/耳（判朝向）。脸上的 10 个点纯属噪声 |
| 3 | **检测框与关键点对应的难度** | 如果复用 Good-Tennis 已有的 RTMPose/YOLO-Pose（top-down），这一步**根本不存在**；只有坚持用 MediaPipe 才会成为难题 |
| 4 | **摄像头实时输入的价值** | 手机摄像头拍网球，机位低、视角斜、抖动、球拍遮挡躯干——**基本不可用**。应以"上传已有视频（最好是高位后方机位）"为主路径 |

### 5.2 被遗漏（8 项，按重要性排序）

| # | 遗漏项 | 为什么重要 | 建议 |
|---|---|---|---|
| 1 | **击球事件切分** | 动作分析的输入锚点，没有它 L3 无的放矢 | 见 R2，纯几何规则，无需训练 |
| 2 | **球员身份绑定与 ID switch** | 两个人的数据不能混；tracker 遮挡后会重分配 ID | 用球衣颜色直方图 + 半区位置做 re-ID，后处理归并；提供手动指定"我是哪一位" |
| 3 | **镜头切分与 homography 分段** | 相机一动，所有位置统计全部失真且静默 | 见 R3 |
| 4 | **评估集与真值** | 没有标注就无法回答"准确率多少"，项目会停在"看着还行" | 建 100–200 个手工标注击球片段的测试集，作为唯一可信指标 |
| 5 | **时间戳统一到帧索引** | wall clock 在抽帧/续跑时必然错位 | 见 1.2 原则一 |
| 6 | **前端坐标叠加的 letterbox 问题** | 骨骼和轨迹会和视频对不上，且很难 debug | `meta` 携带 source/display 尺寸 |
| 7 | **数据量与传输** | 全量 pose 的 JSON 有 40–60 MB，前端会卡 | 见 1.3 体积预算 |
| 8 | **结果置信度的产品化表达** | 分类器一定有误判，用户会当真 | 前端显示置信度 + 低置信度用灰色/虚线 + 提供"标记错误"反馈入口 |

### 5.3 两个工程层面的坑

**MediaPipe 的版本与维护状态**：Google 已把 legacy `mediapipe.solutions.pose` 迁移到 **MediaPipe Tasks (Pose Landmarker)**，旧 API 处于维护模式。且 `mediapipe` 的 PyPI 包**对新版 Python 支持长期滞后**（Python 3.12+ 曾长期装不上）。如果你锁定 Python 3.8–3.10 用旧 API，会与 Good-Tennis 的其他依赖产生版本冲突。这本身就足以成为"改用 RTMPose"的理由。

**依赖冲突**：Good-Tennis 已依赖 PyTorch + Ultralytics + ONNX Runtime + RTMLib。再叠 MediaPipe（自带一套 flatbuffers/absl/protobuf 依赖）会显著增加环境解决难度。少一个栈，少一堆事。

## 6. 改进后的建议方案（分阶段）

### M0 —— 打通基线（1–2 周）
1. 跑通 Good-Tennis 完整流程，用 2–3 段高位后方机位的视频
2. **验证 homography 准确性**：手动量一个已知尺寸（如发球线到网 6.4m），检查映射误差
3. 确认它已有的姿态后端（RTMPose/YOLO-Pose）输出格式，**放弃引入 MediaPipe**
4. 输出 JSONL + summary.json，前端能渲染轨迹和热力图

**出口标准**：一段 5 分钟视频，球员跑动距离、击球点分布看起来合理。

### M1 —— 补上缺失的两层（2–3 周）
5. 镜头切分 + 分段 homography + 几何校验
6. 击球事件切分（球-手腕距离极小值 + 球速矢量突变）
7. 球员身份绑定（球衣颜色 + 半区）+ ID switch 归并
8. **规则版动作分类**（回合首拍=发球；击球点方位=正反手）

**出口标准**：能输出"第 3 回合，近端球员，第 5 拍，正手，置信度 0.87"。

### M2 —— 前端集成（1–2 周）
9. 方式 A+：上传 → job_id → 进度轮询 → 拉 JSON 渲染
10. 视频 + 骨骼 + 轨迹叠加（注意 letterbox）
11. 体积优化（只传事件窗口 pose / 量化 / 下采样）
12. 置信度可视化 + 错误反馈入口

### M3 —— 模型增量（按需，2–4 周）
13. 建 100–200 击球片段的标注测试集
14. 规则版生成伪标签 → 人工复核低置信度 → 训练 SVM/LightGBM
15. **与规则版做 A/B**：只有当模型在测试集上显著超过规则版（> 5 个点）才上线
16. 补上弹跳点、击球速度、旋转估计等增量指标

## 7. 需要你决策的问题

1. **是否接受放弃 MediaPipe，改用 Good-Tennis 内置的 RTMPose / YOLO-Pose？**（我的强烈建议是放弃，理由见 R1 与 5.3）
2. **机位条件是什么？** 是固定的高位后方机位（手机架在看台/围栏），还是手持/侧拍？这直接决定动作分析是否可行——侧拍基本做不了关节角度分析。
3. **单打还是双打？** 双打画面有 4 人，身份绑定和遮挡难度翻倍，Good-Tennis 的双打支持也还在 roadmap 中。
4. **目标用户是谁？** 教练复盘（看重准确率与批量处理）还是爱好者自娱（看重即时反馈与炫酷可视化）？这决定 M2 和 M3 的优先级。
5. **是否有可用的 GPU？** 没有独显的话，方式 B 完全不可行，且必须做任务队列 + 明确的时间预期提示。
