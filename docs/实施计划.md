# Good-Tennis 整合方案 · 修订版实施计划

**前提确认（2026-09-02）**

| # | 决策 | 影响 |
|---|---|---|
| 1 | 放弃 MediaPipe，用内置姿态后端 | 消除 R1，省掉整个 crop 映射链路 |
| 2 | 固定高位后方机位 | **R3 从高风险降为低风险**，且解锁背景建模加速 |
| 3 | 单打 | 身份绑定从"难"降为"简单"（半区 + 球衣色） |
| 4 | 爱好者自娱 | 准确率容忍度提高，**SVM 可以不做**；体验优先级 > 精度 |
| 5 | 无 GPU | 🔴 **性能从次要约束升为首要约束**，方案需围绕它重设计 |

---

## 1. 方案变更对照

| 项目 | 原评估 | 修订后 | 变化 |
|---|---|---|---|
| 姿态模型 | MediaPipe（或 RTMPose） | **RTMPose-t**（256×192，非 m） | 换栈 + 降规格 |
| 人检测 | YOLOv8s | **YOLOv8n** | 降规格 |
| 球检测 | 微调 YOLO @1280 | **背景建模 + ROI 分类**（固定机位红利） | 换算法，成本降 5–10× |
| 推理后端 | ONNX Runtime GPU | **OpenVINO**（Intel）或 ORT CPU + int8 | 换后端 |
| 处理帧率 | 全帧 30fps | **第 1 屏 5fps / 第 2 屏 10fps** | 抽帧 |
| 姿态范围 | 逐帧 | **只在击球候选窗口跑** | 大幅削减 |
| 镜头切分 | 必须做 | **砍掉**，改为机位配置文件 | 删除一个模块 |
| SVM | M3 阶段做 | **直接砍掉**，规则版足够 | 删除一个模块 |
| 身份绑定 | 球衣色 + re-ID + 手动指定 | **半区 + 球衣色**（单打 2 人足够） | 简化 |
| 前端 | 处理完一次性展示 | **渐进式两阶段** | 新增策略 |

**净效果：砍掉 2 个模块，简化 1 个，性能成为设计中心。**

## 2. 无 GPU 性能预算（重算）

### 2.1 朴素实现的灾难

以 8 核桌面 CPU（i5-12400 / R5 5600 级别）、1080p30 为例，**如果直接把 GPU 配置搬到 CPU**：

| 模块 | 配置 | CPU 耗时 |
|---|---|---|
| 人检测 | YOLOv8s @1080p，PyTorch | 200–350 ms |
| 球检测 | 微调 YOLO @1280，PyTorch | 400–700 ms |
| 姿态 | RTMPose-m × 2 人，PyTorch | 200–400 ms |
| **单帧合计** | | **0.8–1.4 s** |

→ 10 分钟视频（18000 帧）= **4–7 小时**。**完全不可用，这是默认路径的真实后果。**

### 2.2 优化后预算

| 模块 | 优化配置 | CPU 耗时 |
|---|---|---|
| 人检测 | YOLOv8n @640，ORT/OpenVINO int8 | 20–35 ms |
| 球检测 | 帧差背景建模 → ROI → 轻量分类 | 15–25 ms |
| 姿态 | RTMPose-t（256×192）int8 × 2 人 | 15–25 ms |
| 追踪/映射/绘图 | NumPy 向量化 | 8–15 ms |
| **单帧合计** | | **60–100 ms** |

### 2.3 端到端时间（10 fps 处理，每 3 帧取 1）

| 视频长度 | 第 1 屏（5fps，仅人检测） | 第 2 屏（10fps 全量） |
|---|---|---|
| **3 分钟** | **≈ 30 秒** | **≈ 2–3 分钟** |
| **10 分钟** | ≈ 1.5–2 分钟 | ≈ 8–15 分钟 |
| 30 分钟 | ≈ 5 分钟 | ≈ 25–45 分钟 |

> 说明：上一版图示中的「30 秒 / 15 分钟」对应 **3 分钟短视频**与**10 分钟视频**两个不同长度。请以本表为准。

### 2.4 优化手段（按性价比排序）

1. **抽帧到 10fps** —— 人体动作带宽 < 5Hz，10fps 对轨迹/姿态完全够用；只有球检测需要高帧率（见第 3 点）。**3× 提速，零成本。**
2. **int8 量化 + OpenVINO** —— YOLO 和 RTMPose 都能导出 ONNX 再转 OpenVINO IR。Intel CPU 上比 ORT CPU 再快 1.5–2×。AMD 则用 ORT + int8。**2–4× 提速。**
3. **背景建模加速球检测** —— 见下节，这是固定机位独有的红利。
4. **姿态只在候选窗口跑** —— 先用球员腕部速度峰值 + 球速突变筛出候选（约 15% 的帧），只对这些帧跑姿态。**再省 60–70% 姿态开销。**
5. **两档模式让用户选** —— 「快速」（5fps + 抽样）与「精细」（10fps 全量），把选择权交给用户，降低等待焦虑。

### 2.5 固定机位的隐藏红利：背景建模

固定机位意味着**背景几乎静态**。这解锁了一个 GPU 上反而不划算、CPU 上却极有价值的优化：

```
1. 维护滑动窗口中值背景（每 30 帧更新一次）
2. 帧差 → 阈值化 → 形态学开闭运算去噪
3. 连通域分析得到候选 blob（尺寸 4–40px、近圆形、高饱和度黄绿色）
4. 只对候选 ROI 跑轻量 CNN 分类（过滤球拍、线、飞虫、边线）
5. 无候选的帧直接跳过，成本≈0
```

成本从 400–700ms 降到 15–25ms，**且召回率通常不低于纯 CNN**（因为 CNN 在 8–15px 小目标上本来就吃力）。这一步是"固定机位"这个前提能换到的最大收益。

## 3. 修订后的架构

### 3.1 机位配置文件（新增，替代镜头切分）

固定机位 → **球场标定只需做一次**，之后所有同机位视频复用。

```json
{
  "profile_name": "后场围栏高位",
  "created_at": "2026-09-02",
  "court_corners_px": [[312, 688], [1608, 688], [1902, 1004], [18, 1004]],
  "homography": [9 floats],
  "validation": {"court_w_m": 10.94, "court_l_m": 23.81, "error_pct": 0.4},
  "baseline_y": 540,
  "near_side_polygon": [[...]],
  "far_side_polygon": [[...]],
  "player_training_bg": "bg_median_v1.png"
}
```

前端提供一次「标定这个机位」流程（复用 Good-Tennis 的手动四点标注），标定后存为 profile。后续上传视频时选 profile 即可，**连自动角点检测都可以跳过**——自动检测在陌生机位上失败率不低，而你是固定机位，没有理由承受这个不确定性。

### 3.2 管线（修订后）

```
上传 → 选机位 profile
     ├─ 阶段 1（5fps，仅 YOLOv8n + 追踪 + 已有 homography）
     │    → 热力图 / 跑动轨迹 / 跑动距离 / 回合列表     ← 结果先出
     └─ 阶段 2（10fps，追加）
          ├─ 背景建模 → 球候选 → CNN 过滤 → 轨迹插值
          ├─ 击球事件切分（球↔腕距极小值 + 球速矢量突变）
          ├─ 候选窗口内跑 RTMPose-t → 关节角度（world landmarks）
          └─ 规则分类（回合首拍=发球 / 击球点方位=正反手）
               → 骨骼叠加 / 击球点 / 动作统计          ← 结果追加
```

### 3.3 砍掉的部分（及理由）

| 砍掉 | 理由 |
|---|---|
| **MediaPipe** | 已确认，RTMPose 自带 track_id 绑定 |
| **镜头切分** | 固定机位，homography 一次标定永久复用 |
| **SVM 训练** | 爱好者场景对准确率容忍度高；规则版覆盖 ~80%，且无需标注成本。若日后真需要，规则版可生成伪标签 |
| **多人 re-ID 模块** | 单打 2 人，半区（网前/网后）+ 球衣颜色直方图足够；ID switch 后用半区位置归并即可 |
| **方式 B 实时流** | 无 GPU，物理上不可行 |

## 4. 分阶段实施计划

### M0 · 基线打通与机位标定（3–5 天）

1. 装 Good-Tennis，跑通完整流程（先用它自带或 1–2 段自拍视频）
2. 确认 RTMPose / YOLO-Pose 后端可用，导出其输出格式样本
3. **验证 homography 精度**：手动量已知距离（发球线到球网 6.40m、边线间距 10.97m），误差应 < 2%
4. 建立机位 profile 文件与标定 UI（复用手动四点标注）
5. 导出 JSONL + summary.json，确认字段与第 1 节 schema 一致

**出口标准**：一段 3 分钟视频，跑动距离和击球点位置看起来合理（能看出球员在底线附近来回）。

### M1 · 性能基线（2–3 天）— 提前做，避免后期返工

6. 导出 YOLOv8n / RTMPose-t 的 ONNX，转 OpenVINO IR，做 int8 量化
7. 写基准脚本：测单模块与整帧耗时，填进 2.2 的表格（**用你自己的 CPU 实测，别信我的估算**）
8. 实现抽帧（5fps / 10fps 两档）
9. 实现背景建模 + ROI 球检测，与纯 CNN 做召回率对比

**出口标准**：10 分钟视频第 2 屏处理时间进入 15 分钟以内。

> ⚠️ **这一阶段必须提前做。** 如果 M1 跑完发现时间是 40 分钟而不是 15 分钟，整个产品形态要改（可能必须上云端 GPU 或强制短片），晚发现代价很大。

### M2 · 事件与分类（5–8 天）

10. 击球事件切分（球↔腕距离极小值 + 矢量突变 + 0.4s 去重）
11. 球员身份：半区判定 + 球衣颜色直方图 + ID switch 归并
12. 候选窗口内跑姿态，**用 world landmarks 算关节角度**（不是 image landmarks）
13. 规则分类：回合首拍=发球 / 击球点方位=正反手 / 击球点高于头顶=高压
14. 建一个 50–100 个击球片段的手工标注集，**只用来测规则版准确率**（不训练模型）

**出口标准**：能输出「第 3 回合，近端球员，第 5 拍，正手，置信度 0.87」，且规则版在标注集上 > 80%。

### M3 · 前端与体验（5–7 天）

15. 方式 A+：上传 → job_id → 进度轮询 → 分阶段拉结果
16. 渐进式渲染：第 1 屏先出，第 2 屏完成后增量追加（带一个"分析完成"提示）
17. 视频 + 骨骼 + 轨迹叠加（**注意 `<video>` 的 object-fit letterbox，用 meta 里的 source/display 尺寸换算**）
18. 体积控制：只传事件窗口 pose + float 量化到 2 位
19. 置信度可视化（低置信度灰色虚线）+ 错误反馈入口
20. **精彩片段自动切片**：用回合检测把视频切成回合短视频 —— 对爱好者的吸引力远高于热力图，成本却很低

**出口标准**：上传 3 分钟视频，30 秒内看到热力图，3 分钟内看到完整分析。

## 5. 关于「没有 GPU」的两条出路

如果 M1 实测后时间仍不可接受：

- **出路 A（推荐）· 云端 GPU 批处理**：Colab 免费 T4 就够（10 分钟视频约 3–5 分钟）。做成「本地上传 → Colab notebook 跑 → 下载 JSON → 本地前端打开」的半自动流程，零成本。若愿意付费，按需 GPU 实例处理一段约几分钱。
- **出路 B · 产品侧约束**：强制短片策略，默认只接受 ≤ 5 分钟视频，并在上传页明确写「3 分钟视频约需 2 分钟分析」。这一条其实**无论有没有 GPU 都该做**——爱好者想看的本来就是自己的几个精彩回合，不是一小时的比赛录像。

## 6. 立即可动手的三件事

1. **装环境 + 跑通 Good-Tennis**，确认姿态后端的输出格式（1 天）
2. **标定你的机位**，用卷尺验证 homography 误差（半天）—— 这个数据决定后续所有位置类统计可不可信
3. **跑 CPU 基准测试**（半天）—— 用你自己的机器填 2.2 那张表，别用我的估算做决策

第 3 件最重要：**先测，再决定产品形态。** 无 GPU 是这个方案里唯一的硬约束，它应该在第一周就被量化清楚，而不是等到 M3 才发现。
