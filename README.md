# TennisLens · AI 网球训练分析

> 用计算机视觉拆解一场业余网球训练：谁在跑、跑了多少、每一拍是正手还是反手。
>
> **核心不是模型有多准，而是如何诚实地处理"模型不准"。**

**[→ 在线演示](https://cq20.github.io/tennis-cv-demo/)** ｜ [技术方案评估](docs/技术方案评估.md) ｜ [实施计划](docs/实施计划.md)

---

## 一、这个产品解决什么问题

业余网球爱好者打完球，想知道的无非三件事：

- 我今天跑了多少、跑动分布合不合理
- 我的正反手使用比例是否失衡
- 有没有几个回合值得回看

职业队有 Hawk-Eye 和多机位系统，爱好者什么都没有。本项目尝试用**一台固定机位的手机 + 纯 CPU 推理**，把这件事的成本压到接近零。

**目标用户**：业余爱好者（非职业队）。这个定位直接决定了三个设计取舍：

| 定位带来的判断 | 结论 |
|---|---|
| 准确率容忍度可以提高 | 85% 够用 → **砍掉 SVM，用规则法** |
| 等待时间是硬指标 | 无法实时 → **渐进式两阶段出结果** |
| 可视化要有吸引力 | 热力图不如**回合自动切片**有意思 |

## 三、三个关键技术判断

### 1. 放弃 MediaPipe，改用 top-down 姿态模型

MediaPipe Pose 是**单人**模型且不带 `track_id`。网球画面有两个人，全图跑 `num_poses=2` 会出现关键点在两人之间跳变、遮挡时"串人"。

改用 **RTMPose**（top-down）后，直接复用 YOLO 的检测框和 `track_id`，**身份绑定是免费的**，还省掉一整套 crop→推理→坐标映射链路。

### 2. 补上缺失的一层：击球事件切分

原方案直接从"逐帧检测"跳到"动作分类"，这里有个致命断层——**正手和反手在远离击球点的帧上，关节角度分布高度重叠**，逐帧分类等于随机猜测。

必须先定位击球瞬间：

```
球 ↔ 持拍侧手腕距离曲线 → 取局部极小值
      + 球速矢量夹角突变 > 60° 二次确认
      + 0.4s 最小间隔去重
```

拿到 contact 帧后，**只在 ±15 帧窗口内提取特征**。这一步无需任何训练数据，纯几何规则。

### 3. 用 world landmarks 而非 image landmarks 算角度

2D 关键点算出的是**投影角度**，不是真实三维关节角。侧机位下前臂投影误差可达 30–40°，足以让分类器全盘失效。

关节角度的泛化性瓶颈**不是身高体型**（角度本身尺度不变），而是**相机视角**。

## 四、AI 能力边界（本项目的重点）

大多数 CV demo 只展示"能做什么"。这个项目的一半篇幅在说明**不能做什么**——主动划边界是 AI 产品经理最重要的能力之一。

### ✅ 能做

| 能力 | 预期 | 说明 |
|---|---|---|
| 跑动与位置统计 | 误差 ±0.3m | 固定机位标定后**最可信**的一类指标 |
| 击球事件检测 | 召回 ~90% | 无需训练数据 |
| 正反手 / 发球分类 | 85–92% | 规则法：回合首拍=发球，击球点方位=正反手 |
| 关节角度参考 | 趋势可用 | 绝对角度存在投影畸变 |

### ❌ 明确不做

| 不做 | 原因 |
|---|---|
| **技术动作质量评分** | "这一拍标不标准"需要教练标注数据 + 时序模型。宁可不做，也不误导用户 |
| **球速 / 旋转估计** | 30fps 下球每帧移动 1–2m，亚像素误差被放大数十倍，数值不可信 |
| **移动机位 / 手持拍摄** | 相机移动会让 homography 失效且**静默出错**（图很漂亮，数字全错） |

### 不确定性的产品化处理

- **三级置信度**：高=实心、中=半透明、低=**灰色虚线 + "待确认"标签**。不让用户把猜测当结论
- **人工纠错闭环**：每个事件可改判，沉淀为伪标签，低置信样本优先人工复核
- **等待预期管理**：第 1 屏（热力图/轨迹）30 秒–2 分钟先出，第 2 屏（骨骼/动作）后台追加

## 五、围绕"没有 GPU"重新设计

这是本项目唯一的物理约束，也是设计的出发点。

### 朴素做法会怎样

直接把 GPU 配置搬到 CPU：**0.8–1.4 秒/帧 → 10 分钟视频要跑 4–7 小时**。产品直接不成立。

### 优化路径

| 手段 | 收益 | 理由 |
|---|---|---|
| 抽帧到 10fps | 3× | 人体动作带宽 <5Hz，全帧率纯属浪费 |
| int8 量化 + OpenVINO | 2–4× | YOLO / RTMPose 均可导出 ONNX 再转 IR |
| **背景建模加速球检测** | **5–10×** | 见下，这是固定机位独有的红利 |
| 姿态只在候选窗口跑 | 省 60–70% | 先筛后算 |

**背景建模**：固定机位意味着背景几乎静态 —— 中值背景 → 帧差 → 连通域筛出 4–40px 的近圆形黄绿色 blob → 只对候选 ROI 跑轻量 CNN。成本从 400–700ms 降到 15–25ms，且召回通常不降反升（8–15px 的小目标，纯 CNN 本来就吃力）。

**结果**：3 分钟视频约 2–3 分钟，10 分钟视频约 8–15 分钟。

## 六、推理管线

```
1. 视频解码与抽帧      FFmpeg → 10fps
2. 球员检测与追踪      YOLOv8n @640 · int8 → bbox + track_id
3. 背景建模 + 球检测   中值背景 → 帧差 → blob 候选 → 轻量 CNN 过滤
4. 球场坐标映射        机位 profile 预标定 homography（一次标定永久复用）
5. 击球事件切分        球-腕距离极小值 + 速度矢量突变
6. 姿态估计            RTMPose-t，仅击球 ±15 帧窗口运行
7. 规则分类 + 置信度   回合首拍=发球；击球点方位=正反手
```

数据流以**帧索引**（而非 wall clock）为主键，逐帧结果写 JSONL，聚合结果写 JSON。详见 [实施计划](docs/实施计划.md)。

## 七、当前状态与下一步

### ⚠️ 关于演示数据

在线演示中的**比赛画面、骨骼、轨迹均为程序化生成的确定性模拟数据**。原因有二：缺少真实视频素材；无 GPU 环境下跑真实推理需数十分钟。

但**数据格式与真实管线输出完全一致**（帧索引主键、JSONL schema、事件结构），推理管线接入后可直接替换数据源，**前端代码无需改动**。

### 已明确的最大短板

**没有评估集。** 文档中出现的所有准确率均为基于公开 benchmark 的**估计值，非实测值**。在没有标注集之前，本项目不对外声称任何准确率数字。

### 下一步

1. **建评估集**（最高优先级）—— 100–200 个手工标注的击球片段。必须**按视频切分**而非按样本随机切分，否则同一视频的帧高度相关，会严重高估准确率
2. **跑通真实视频链路** —— 用真实机器校准 CPU 性能估算
3. **数据闭环产品化** —— 用户改判沉淀为伪标签，优先复核低置信样本
